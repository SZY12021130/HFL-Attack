# 门限 CKKS 解密：安全性视角的完整分析

> 本文档系统梳理门限（Threshold）CKKS 解密的全部技术细节：标准 CKKS 加解密公式、
> 私钥的秘密共享（加法共享 / Shamir）、有无可信机构（TTP / DKG）两种模式的完整流程、
> 部分解密结果发给谁的安全分岔、以及各实体在每种方案下"知道什么、能做什么"。
> 面向 HFL-Attack 项目的可插拔 `threshold` 模块设计（见 §10）。

---

## 1. 预备：标准 CKKS 加解密公式

CKKS 的明文空间是 $\mathbb{C}^{n/2}$（$n$ 为分圆多项式次数），通过编码（Encode）
嵌入到分圆多项式商环 $R_q = \mathbb{Z}_q[X]/(X^n+1)$，加解密在 $R_q$ 上进行。

### 1.1 密钥生成

$$
sk = s \leftarrow \chi_s \quad(\text{小系数多项式})
$$
采样随机 $a \leftarrow R_q$ 和噪声 $e \leftarrow \chi_e$，计算公钥：
$$
pk = (b, a), \qquad b = -a \cdot s + e \pmod q
$$
**关键事实**：公钥由私钥派生，任何生成 $pk$ 的实体在生成瞬间必然知道 $sk$
（这是 TTP 模式必须有可信机构的根本原因，见 §4）。

### 1.2 加密

对编码并缩放后的明文 $\Delta m$（$\Delta = 2^p$ 为 scale），采样 $u \leftarrow \chi_s$、
$e_1, e_2 \leftarrow \chi_e$：

$$
c_0 = b \cdot u + e_1 + \Delta m, \qquad
c_1 = a \cdot u + e_2 \pmod q
$$
密文 $ct = (c_0, c_1) \in R_q^2$（重线性化后的标准形式）。

### 1.3 解密

$$
c_0 + c_1 \cdot s
= (b u + e_1 + \Delta m) + (a u + e_2) s
= \Delta m + \underbrace{(e_1 + e_2 s) - e u}_{\text{总噪声 } e_{\text{tot}}} \pmod q
$$
解码：$m \approx \dfrac{c_0 + c_1 s}{\Delta}$，要求 $|e_{\text{tot}}| \ll \Delta/2$。

**门限解密的核心观察**：解密运算关于 $s$ 是**线性的**。$c_1 \cdot s$ 这一项对 $s$ 线性，
因此任何对 $s$ 的线性秘密共享，都直接诱导出 $c_1 \cdot s$ 的共享——这就是部分解密可行性的代数基础。

## 2. 威胁模型与实体

| 实体 | 行为模型 | 目标 |
|---|---|---|
| 服务器（云） | honest-but-curious：严格执行协议，但试图从所见消息中推断 | 想拿到明文更新/模型 |
| 客户端 | 大多数诚实；最多 $f$ 个恶意（$f < t$） | 诚实客户端保护本地数据 |
| Dealer（仅 TTP 模式） | 完全可信 | Setup 时分发密钥，之后离线 |
| Combiner（组合器） | 执行拉格朗日组合的实体 | 拿到明文（按设计） |

**合谋假设**：安全性以"敌手控制的实体数 < 门限 $t$"为界。$t$ 个客户端合谋可以恢复
任何密文的明文（这是 $t$-out-of-$n$ 的定义，也是设计目标）；低于 $t$ 个则信息论安全。

## 3. 私钥秘密共享的两种方式

### 3.1 加法秘密共享（$n$-out-of-$n$）

私钥拆成 $n$ 份随机份额，满足：
$$
s = s_1 + s_2 + \dots + s_n \pmod q
$$
**部分解密**：参与方 $i$ 计算 $d_i = c_1 \cdot s_i \pmod q$。

**组合**（必须全员参与）：
$$
c_0 + \sum_{i=1}^n d_i = c_0 + c_1 \sum_i s_i = c_0 + c_1 s = \Delta m + e_{\text{tot}}
$$

- ✅ 计算极简，无插值开销
- ❌ 无容错：任一方掉线则无法解密
- 适用：参与方固定、无掉线的场景

### 3.2 Shamir 秘密共享（$t$-out-of-$n$）★ 主流

Dealer 构造 $t-1$ 次随机多项式 $f(x) = s + a_1 x + \dots + a_{t-1} x^{t-1}$，
满足 $f(0) = s$。参与方 $i$ 持有份额 $s_i = f(i)$。

**部分解密**：$d_i = c_1 \cdot s_i \pmod q$。

**组合**（任意 $t$ 个参与方，索引集 $S$）：先算 Lagrange 插值系数
$$
\lambda_i = \prod_{\substack{j \in S \\ j \neq i}} \frac{-j}{i - j} \pmod q
$$
（分母求逆要求 $q$ 的素因子均大于 $\max |i-j|$；CKKS 的 $q = \prod p_k$
是多个素数乘积，工程上需保证 $p_k > n$，见 §9。）

由插值恒等式 $\sum_{i \in S} \lambda_i f(i) = f(0) = s$：
$$
c_0 + \sum_{i \in S} \lambda_i d_i
= c_0 + c_1 \sum_{i \in S} \lambda_i s_i
= c_0 + c_1 s = \Delta m + e_{\text{tot}}
$$

- ✅ 容错：任意 $t$ 方即可解密，适配 FL 客户端不稳定场景
- ✅ 安全：$t-1$ 个份额信息论独立于 $s$（多项式随机性）
- ❌ 少量插值开销（可忽略）

**$d_i = c_1 \cdot s_i$ 本身就是一个 Shamir 共享**：因为映射 $s_i \mapsto c_1 s_i$
是线性的，$d_i = f'(i)$ 其中 $f'(x) = c_1 f(x)$ 仍是 $t-1$ 次多项式且
$f'(0) = c_1 s$。组合 $d_i$ 等价于直接插值出 $c_1 s$——**整个门限解密就是
"对私钥做一次 Shamir，密文第一分量 $c_1$ 作为线性算子作用上去"**。

## 4. TTP 模式：可信分发者

### 4.1 为什么必须有可信机构

由 §1.1，$pk = (-a s + e, a)$ 必须由知道 $sk$ 的一方算出。TTP 模式下这个"一方"
就是 Dealer：

1. Dealer 生成 $(pk, sk)$ —— **此瞬间 Dealer 知道完整私钥**；
2. Dealer 广播 $pk$；
3. Dealer 用 §3 的方式把 $sk$ 拆成 $n$ 份份额，**经加密通道**分发给 $n$ 个客户端；
4. Dealer 离线/销毁。

**结论：TTP 模式的可信性需求压缩在 Setup 一瞬间，但确实需要一个 Dealer。**
若不想引入 Dealer，必须走 §5 的 DKG。

### 4.2 每轮解密流程

```
Setup（一次性）:
  Dealer: (pk, sk) ← KeyGen
  Dealer: {s_1,...,s_n} ← Share(sk, t, n)     # Shamir 或加法
  Dealer → 全体: pk（公开）
  Dealer → 客户端 i: s_i（加密通道，仅此一次）

每轮:
  服务器: ct = (c0, c1)（密文加权聚合结果）
  服务器 → 被选客户端: 广播 c1
  客户端 j: d_j = c1 · s_j + e'_j              # 部分解密 + smudging 噪声
  ... d_j 的去向见 §6（核心安全分岔）...
  组合器: Δm ≈ (c0 + Σ λ_j d_j) / Δ
```

### 4.3 安全性分析

| 攻击面 | 分析 |
|---|---|
| 服务器拿到 $pk$、所有密文 | 无解密密钥分量，CKKS/RLWE 困难性保护 |
| 服务器拿到 $t-1$ 个份额 | Shamir $t-1$ 份信息论独立，无法重构 |
| 恶意客户端合谋 ≥ $t$ 个 | 可恢复明文——这是 $t$-out-of-$n$ 的固有上界，选 $t$ 时保证恶意数 $< t$ |
| **客户端互相重建 $sk$**（不安全用法） | 若把份额凑齐恢复出完整 $sk$ 再解密，恢复方永久持钥，退化为单密钥——**工程上禁止，必须用部分解密** |
| Dealer 被攻陷 | Setup 期一次性信任假设；事后 Dealer 不存在则无持续攻击面 |

## 5. DKG 模式：无可信机构的分布式密钥生成

Pedersen DKG（Gennaro et al.）让 $n$ 个客户端**各自生成一个本地多项式**，
通过交换份额构造出一个**没有人知道的**全局私钥。

### 5.1 流程

```
Setup（每个客户端 i 本地执行）:
  客户端 i: 随机选 t-1 次多项式 f_i(x)，本地秘密 s_i = f_i(0)
  客户端 i: 生成承诺 C_{i,k} = g^{a_{i,k}} · h^{r_{i,k}}（可验证，防作弊）
  客户端 i → 客户端 j: 份额 f_i(j)（加密到 j 的公钥！见 5.2）

  客户端 j（收到全部 i 的份额后）:
    验证每个 f_i(j) 对应承诺
    聚合自己的全局份额: s_j = Σ_i f_i(j)
    （全局多项式 F(x) = Σ_i f_i(x)，s_j = F(j)，F(0) = sk = Σ_i f_i(0)）

  公钥的集体生成（RLWE 方式）:
    客户端 i 广播公钥贡献 b_i = -a · f_i(0) + e_i
    全局公钥 pk = (Σ_i b_i, a) = (-a·sk + Σ e_i, a)
    —— 与标准 CKKS 公钥同构，但没有任何人知道 sk = Σ_i f_i(0)
```

### 5.2 份额怎么交换：P2P 还是经服务器？

| 方式 | 安全性 | 结论 |
|---|---|---|
| P2P 直连 | 服务器完全不见份额 | 最安全，设备多时工程不现实 |
| **服务器转发 + 份额加密到接收方公钥** | 服务器只见密文份额，无法重构任何 $f_i$ | ✅ **FL 标准做法**（与 PPBR 的 SA 私钥分片分发同构） |
| 服务器转发明文份额 | ❌ 服务器收集 $t$ 个 $f_i(j)$ 即可恢复 $f_i(0)=s_i$，进而恢复 $sk$ | 绝对禁止 |

### 5.3 安全性分析

- **无 TTP**：$sk$ 从未以完整形态存在于任何实体（包括 Setup 期）。
- **诚实多数假设**：Pedersen DKG 的正确性要求恶意方 $< n/2$（作恶者可以拒绝贡献使
  协议中止，但不能让诚实方接受错误的 $sk$）；若只要求可用性，配 VSS（可验证秘密共享）。
- **合谋上界**：$\geq t$ 个客户端合谋可解密任意密文（同 §4.3）。

## 6. 部分解密发给谁：三种场景（核心安全分岔）

部分解密值 $d_j = c_1 \cdot s_j + e'_j$ 的去向，决定服务器能否恢复明文。

### 场景 A：服务器做组合器（服务器可解密聚合结果）

```
客户端 j → 服务器: d_j（明文形式）
服务器: Δm ≈ (c0 + Σ_{j∈S} λ_j d_j) / Δ
```

- **服务器每轮拿到聚合更新/全局模型的精确明文**。
- 隐私退化为**聚合级**：单个客户端更新仍不可见（受聚合保护），但服务器拥有
  全局模型的完整轨迹。
- 残余风险：① 对聚合更新做梯度反演（生成先验可显著增强，LLM 时代尤甚——
  Wang et al. 2026 的动机）；② 多轮差分追踪推断成员信息；③ 自适应投毒。
- **适用**：cross-silo FL 中全局模型本来就对服务器公开的场景。此时门限解密对
  服务器不提供额外隐私，价值只剩**无私钥单点 + $t$-out-of-$n$ 掉线容忍**。
- **不适用**：本项目原始目标"服务器拿不到明文、只有客户端能解密"。

### 场景 B：指定客户端做组合器（服务器盲）★ 推荐

```
服务器 → 全体被选客户端: 广播 c1
客户端 j: d_j = c1·s_j + e'_j
客户端 j → 服务器: Enc_pk_comb(d_j)     ← 用组合器公钥加密！
服务器 → 组合器: 转发 Enc_pk_comb(d_j)（服务器只见密文）
服务器 → 组合器: c0
组合器: 解密各 d_j，Δm ≈ (c0 + Σ λ_j d_j) / Δ
组合器 → 全体客户端: 广播明文全局模型（或群组密钥加密后广播）
```

- 服务器有 $c_0$ 但只有 `Enc(d_j)`，**凑不齐 $t$ 个明文份额，无法解密**。
- 组合器是客户端，知道全局模型是设计允许（客户端本来就需要它训练）。
- 进阶：若连最终模型都不想让服务器旁听，组合器用**客户端群组密钥**（一次额外
  DKG 建立）加密明文模型再广播。
- **这是"服务器不持私钥"目标下的标准实现。**

### 场景 C：LSS 二次保护（Wang et al. 2026, CDKS-LSS）

针对场景 A 中"服务器当组合器会恢复个体明文"的泄漏（多密钥 HE 场景尤为致命）：

```
客户端 i: d_i = c1·s_i + e'_i
客户端 i: 把 d_i 再做一次 Shamir → 份额 {δ_{i,j}}，δ_{i,j} 发给客户端 j
客户端 j: 汇总 σ_j = Σ_i δ_{i,j}（或带 Lagrange 权重）
客户端 j → 服务器: σ_j
服务器: 需收集 t 个 σ_j 才能重构明文；任何单个 σ_j / δ_{i,j} 都无信息
```

- 服务器**可以**当组合器，但从所见消息中恢复不出任何个体 $d_i$，更恢复不出个体更新。
- 安全性升级：把解密阶段的机密性从计算安全提升到**信息论安全**（LSS 对 $t-1$ 合谋）。
- 代价：多一轮份额分发，通信/计算显著增加。

### 三种场景对比

| | 场景 A（服务器组合） | 场景 B（客户端组合） | 场景 C（LSS） |
|---|---|---|---|
| 服务器看到全局明文 | ✅ 能 | ❌ 不能 | ❌ 不能 |
| 服务器看到个体更新 | 不能（聚合保护） | ❌ 不能 | ❌ 不能（信息论级） |
| 掉线容忍 | $t$-out-of-$n$ | $t$-out-of-$n$ | $t$-out-of-$n$ |
| 通信开销 | 低 | 低 | 高 |
| 适用 | 模型对服务器公开 | 服务器必须盲（本项目目标） | 服务器组合 + 个体级防泄漏 |

## 7. Wang 2026 的泄漏案例精确分析

**多密钥 HE（如 CDKS）的 naive 门限解密**：

- 客户端 $i$ 用自己的 $pk_i$ 加密自己的更新，密文 $ct_i = (c_{i,0}, c_{i,1})$；
- 服务器同态聚合后，解密需要每个客户端 $i$ 提供 $\mu_i = c_{i,1} \cdot sk_i$；
- **泄漏**：客户端 $i$ 把 $\mu_i$ 直接发给服务器 ⇒ 服务器持有 $c_{i,0}$ 与 $\mu_i$
  两者，立即恢复**客户端 $i$ 一个人的明文更新**：
  $$
  c_{i,0} + \mu_i = c_{i,0} + c_{i,1} sk_i = \Delta m_i + e
  $$
  无需合谋、无需其他参与方——单点泄漏。

**单密钥聚合场景的对照**：聚合密文只有一个 $(c_0, c_1)$，$t$ 个 $d_j$ 恢复的是
**全局更新**而非个体更新。因此单密钥场景的威胁是"服务器看全局"（场景 A），
多密钥场景的威胁是"服务器看个体"（更严重）。CDKS-LSS 用 LSS 保护 $\mu_i$
同时解决了两者。

## 8. 总表：各实体知道什么、能做什么

| 实体 | 持有 | 能解密什么 | 不能做什么 |
|---|---|---|---|
| 服务器（场景 B/C） | $pk$、全部密文、加密后的 $d_j$、$c_0$ | 什么都解不开 | 无法恢复任何明文（除非合谋 ≥ $t$ 客户端） |
| 服务器（场景 A） | 同上 + 明文 $d_j$ | 聚合更新/全局模型 | 无法恢复个体更新 |
| 客户端 | $s_j$、$pk$、$c_1$、自己的数据 | 与其他 ≥ $t-1$ 方合作可解任意密文 | 单独无法解密；无法知道完整 $sk$（DKG 模式） |
| Dealer（仅 TTP） | Setup 期短暂持有 $sk$ | Setup 期一切 | 离线后无能力 |
| 组合器（客户端） | 收到的 $t$ 个 $d_j$、$c_0$ | 本轮聚合明文 | 不知道 $sk$，无法解密**其他**密文 |

**合谋边界**：
- 任意 $< t$ 个客户端合谋：无法解密（Shamir 信息论安全）；
- ≥ $t$ 个客户端合谋：可解密所有密文（$t$-out-of-$n$ 的定义，不可避免）；
- 服务器 + $< t$ 个客户端合谋（场景 B/C）：仍无法解密；
- 服务器 + $\geq t$ 个客户端：可解密（服务器拿到 $t$ 个明文 $d_j$）。

## 9. CKKS 工程注意事项

1. **Smudging 噪声**：部分解密值 $d_j = c_1 s_j + e'_j$ 中的 $e'_j$ 不可省。
   裸发 $c_1 s_j$ 在 chosen-ciphertext 敌手面前可能泄露 $s_j$ 信息；$e'_j$ 要足够大，
   使重构后的总噪声仍满足 $|e_{\text{tot}} + \sum e'_j| < \Delta/2$。
2. **Lagrange 分母可逆性**：$q$ 的所有素因子必须大于客户端编号差（实践中素因子
   都是大素数，天然满足，但实现时应断言）。
3. **门限重线性化**：若密文需要乘法（如加权平均在密文上做标量乘），乘法产生
   $(c_0, c_1, c_2)$ 三项，需要各方合作生成/使用**共享的重线性化密钥**
   （collective relinearization key）压回两项。加法聚合不需要。
4. **份额序列化**：TenSEAL 的 $sk$ 序列化约 193KB，按 64 字节分块做 Shamir
   （复用 `ppbr/sa.py` 的 `shamir_split`，素数域 $2^{521}-1$），恢复时拼接。
5. **TenSEAL 的限制**：CKKSVector 不暴露 $c_0/c_1$ 分量，无法在真实 TenSEAL
   密文上做部分解密。本项目的处理：协议层用真实 Shamir/DKG 数学 + 理想解密
   预言机完成功能仿真，`threshold/toy_ckks.py` 用教科书 CKKS（numpy）完整
   验证门限解密公式；真实化路线是迁移 OpenFHE（原生
   `MultipartyKeyGen` / `MultipartyDecryptLead/Active`）或 Lattigo（mpCKKS）。

## 10. 与 HFL-Attack 项目的关系

### 10.1 现状（未开门限）

- CKKS 轨道：单密钥对，**完整 $sk$ 分发给所有客户端**（`main.py:278-281`），
  服务器只持公钥。功能正确，但存在"客户端共享全局私钥"的单点：
  任一客户端可解密全局模型；若客户端数量大，私钥分发面大。
- PPBR 轨道：不用 CKKS 门限，走论文的 SA（X25519 + Shamir 私钥备份）体系。

### 10.2 可插拔 `threshold` 模块规划

```yaml
threshold:
  enabled: false
  mode: "ttp"        # ttp=可信分发（§4） | dkg=无可信机构（§5）
  t: 5               # 门限（§3.2）
  smudging: true     # 部分解密加噪（§9.1）
  combiner: "client" # 组合器：client（场景 B，推荐）| server（场景 A）
```

- `sharing.py`：$sk$ 分块 Shamir 分片（复用 `ppbr/sa.py`）；
- `dkg.py`：Pedersen DKG（承诺-验证-份额聚合，§5.1）；
- `toy_ckks.py`：教科书 CKKS + 真·部分解密，端到端验证 §3、§6 全部公式；
- `ceremony.py`：每轮解密仪式编排（§6 场景 B 的消息流），记录份额字节数、
  仪式耗时等指标。

### 10.3 威胁模型对应

| 你的需求 | 配置 |
|---|---|
| 允许服务器看聚合模型（要掉线容忍） | `mode: ttp, combiner: server`（场景 A） |
| 服务器必须盲（原项目目标） | `mode: dkg, combiner: client`（§5 + 场景 B）★ |
| 防服务器组合器 + 个体级防泄漏 | 场景 C（LSS），后续迭代 |
